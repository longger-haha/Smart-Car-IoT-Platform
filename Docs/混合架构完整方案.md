## 混合架构完整方案

---

### 一、设计总纲

**核心原则：ESP32 负责实时生存，后端负责全局智慧**

```
ESP32 = 脊髓反射（毫秒级，无条件执行，保命优先）
后端  = 大脑皮层（百毫秒级，全局规划，策略优化）
通信  = 神经系统（MQTT 双向，分级通道）
```

**一句话概括**：ESP32 能自己跑，后端让它跑得更好；后端断了，ESP32 降级但不失控。

### 二、ESP32 端架构

#### 2.1 双核分工

```
┌─ Core 0 (PRO CPU) ──────────────────────────────────┐
│  优先级 3: WiFi/MQTT 通信栈                          │
│  优先级 2: 遥测上报 (1Hz)                            │
│  优先级 1: 指令接收 + 配置更新                        │
│  优先级 0: WiFi 扫描 (异步, 30s 一次)                 │
└──────────────────────────────────────────────────────┘

┌─ Core 1 (APP CPU) ──────────────────────────────────┐
│  优先级 4: 安全守护 (50Hz, 20ms 周期)                │
│           → 超声波 < 15cm → 立即停车                  │
│           → 断网 10s → 自动停车                       │
│  优先级 3: 导航决策 (10Hz, 100ms 周期)               │
│           → 行为树 tick                              │
│           → VFH+ + 简化 DWA                          │
│           → Pure Pursuit                             │
│  优先级 2: IMU 融合 (100Hz, 10ms 周期)               │
│  优先级 1: 传感器采集 (10Hz)                          │
│  优先级 0: 栅格地图更新 (10Hz)                        │
└──────────────────────────────────────────────────────┘
```

**为什么这样分配**：

- Core 0 跑通信：WiFi/MQTT 有阻塞调用，不能和实时决策抢 CPU
- Core 1 跑决策：安全守护最高优先级，导航决策次之
- 安全守护独立于导航：即使导航决策卡死，安全守护仍能停车

#### 2.2 ESP32 软件模块

| 模块 | 频率 | 内存 | 职责 |
|------|------|------|------|
| 安全守护 | 50Hz | <100B | 紧急停车、断网保护、电池监测 |
| IMU 融合 | 100Hz | <100B | 互补滤波 + 航向输出 |
| 栅格地图 | 10Hz | ~2KB | 25×25 局部地图，传感器融合 |
| VFH+ | 10Hz | ~700B | 18 扇区方向选择（查表优化） |
| 简化 DWA | 10Hz | <200B | 12 候选速度对评估 |
| Pure Pursuit | 10Hz | <100B | 航点路径跟踪 |
| 行为树 | 10Hz | ~500B | 决策编排 |
| 遥测上报 | 1Hz | ~1KB | 精简遥测 + 导航状态 |
| 指令接收 | 事件驱动 | ~500B | 航点/配置/覆盖指令 |

**总内存占用：~5KB**，远在 ESP32 可用范围内。

#### 2.3 ESP32 行为树

```
Root (Selector — 优先级从高到低)
│
├── [1] Safety (Sequence)
│   ├── 电池 < 10V? → 停车 + 上报
│   └── 断网 > 10s? → 停车
│
├── [2] Emergency (Sequence)
│   ├── 超声波 < 15cm? → 立即停车
│   └── 等待 500ms → 重新评估
│
├── [3] ObstacleAvoid (Sequence)
│   ├── VFH+ 检测到需要绕行?
│   ├── 简化 DWA 选方向
│   └── 下发差速
│
├── [4] WaypointNav (Sequence)
│   ├── 有未到达航点?
│   ├── Pure Pursuit 跟踪
│   ├── 检查航点到达
│   └── 下发差速
│
├── [5] FreeCruise (Sequence)
│   ├── 无航点模式?
│   ├── VFH+ 选最安全方向直行
│   └── 下发差速
│
└── [6] Idle → 停车
```

#### 2.4 ESP32 降级策略

| 后端状态 | ESP32 行为 |
|---------|-----------|
| 在线 + 有航点 | 按后端下发的航点巡航 |
| 在线 + 无航点 | 自由巡航（VFH+ 避障直行） |
| 断网 < 5s | 继续当前行为，缓存遥测 |
| 断网 5~10s | 减速到 50%，继续避障 |
| 断网 > 10s | 停车，等待重连 |
| 重连成功 | 上报断网期间状态，接收新指令 |

### 四、通信协议设计

#### 4.1 MQTT 主题规划

```
═══ 上行 (ESP32 → 后端) ═══

sensor/<device_id>           遥测数据 (1Hz, 精简版)
  → 温度、湿度、超声波、红外、PWM、电池、序列号
  → 不再包含 IMU 原始数据（ESP32 本地已融合）

sensor/<device_id>/nav       导航状态 (1Hz)
  → 航向角、当前航点索引、行为树状态、VFH 方向
  → 左右轮 PWM、速度

sensor/<device_id>/grid      栅格快照 (0.2Hz, 每5秒)
  → 25×25 occupancy 数组压缩后上报
  → 用于后端可视化和长期地图构建

sensor/<device_id>/event     导航事件 (事件驱动)
  → 航点到达、紧急停车、避障触发、断网恢复等

heartbeat/<device_id>        心跳 (0.5Hz)


═══ 下行 (后端 → ESP32) ═══

command/<device_id>          即时指令 (事件驱动)
  → {cmd: "stop"} / {cmd: "diff", pwm_l, pwm_r}
  → 仅用于手动控制覆盖

route/<device_id>            航点路线 (事件驱动)
  → {waypoints: [{lat, lng}, ...], speed_pwm: 160}
  → 后端规划的全局路径

config/<device_id>           参数配置 (事件驱动)
  → {behavior_style, cruise_speed, safe_distance_cm, 
  →  vfh_alpha, pid_kp, pid_kd, ...}

behavior/<device_id>         行为树更新 (事件驱动)
  → {tree: "base64编码的行为树定义"}

override/<device_id>         模式覆盖 (事件驱动)
  → {mode: "manual"} → ESP32 停止自主决策，接受 command
  → {mode: "auto"}   → ESP32 恢复自主决策
```

#### 4.2 遥测数据精简

```
当前遥测 JSON (~500B):
  device_id, temperature, humidity, ultrasonic_cm,
  ir_l, ir_r, imu_ax, imu_ay, imu_az,
  imu_gx, imu_gy, imu_gz, imu_heading,
  speed_pwm, seq, wifi_aps[6], signature

精简后遥测 JSON (~200B):
  device_id, ultrasonic_cm, ir_l, ir_r,
  heading(融合后), speed_pwm, bat_mv, seq,
  wp_index, nav_state, signature

变化:
  ❌ 删除 imu_ax/ay/az/gx/gy/gz (ESP32本地融合)
  ❌ 删除 temperature/humidity (非导航关键)
  ❌ 删除 wifi_aps (降低频率到30s一次)
  ✅ 新增 heading (融合后航向)
  ✅ 新增 bat_mv (电池电压)
  ✅ 新增 wp_index, nav_state (导航状态)
```

#### 4.3 栅格快照压缩

```
25×25 = 625 bytes 原始数据

压缩方案:
  - occupancy 只保留高4位 → 313 bytes
  - RLE 编码 → ~150 bytes (典型场景)
  - Base64 → ~200 bytes

每 5 秒上报一次，带宽: ~40 bytes/s — 完全可接受
```

### 六、关键场景流程

#### 6.1 自动巡航完整流程

```
1. 用户在前端地图上点选航点
2. 前端 POST /api/vehicle/route/plan → 后端 A* 规划
3. 后端返回优化后的航点序列
4. 用户确认 → POST /api/vehicle/route/dispatch
5. 后端 MQTT 发布 route/<device_id> {waypoints, speed}
6. ESP32 收到航点 → 存入本地 → 行为树 WaypointNav 节点激活
7. ESP32 每 100ms 自主决策:
   a. 安全守护: 超声波 < 15cm → 停车
   b. VFH+: 检测障碍方向
   c. 简化 DWA: 选择绕行速度
   d. Pure Pursuit: 跟踪航点
   e. 下发差速指令到电机
8. ESP32 每 1s 上报导航状态
9. 前端轮询展示实时位置 + 栅格地图
10. 到达终点 → ESP32 上报事件 → 行为树切到 Idle
```

#### 6.2 紧急避障流程

```
1. ESP32 安全守护任务 (50Hz) 读取超声波: 12cm
2. 立即停车 (1ms 内)
3. 上报 event: {type: "EMERGENCY_STOP", distance_cm: 12}
4. 后端收到 → 写审计日志 → 前端告警
5. ESP32 行为树 Emergency 节点激活
6. 等待 500ms → 重新读取超声波
7. 障碍仍在 → VFH+ 选绕行方向 → 简化 DWA → 绕行
8. 障碍清除 → 行为树回到 WaypointNav → 继续航点
9. 全程无需后端参与决策
```

#### 6.3 参数调优流程

```
1. 前端参数面板显示当前参数
2. 用户拖动滑块: safe_distance_cm 50 → 80
3. PUT /api/vehicle/config/<id> {safe_distance_cm: 80}
4. 后端 MQTT 发布 config/<device_id>
5. ESP32 收到 → 更新本地 VFH+ 参数
6. 下一次 VFH+ 计算 (100ms 内) 自动使用新参数
7. 无需重启，无需烧录
```

#### 6.4 断网降级流程

```
1. ESP32 检测到 MQTT 断连
2. 继续当前导航行为（航点已存在本地）
3. 5s 内: 正常巡航 + 避障
4. 5~10s: 减速到 50%，继续避障
5. > 10s: 停车，等待重连
6. 重连成功:
   a. 上报断网期间缓存的导航事件
   b. 请求后端最新配置: config/<id>?sync=1
   c. 后端下发最新航点/配置
   d. 恢复巡航
```

#### 6.5 多车协同流程

```
1. 两辆车 A、B 同时收到航点任务
2. 后端多车调度器检测到路径交叉
3. 后端计算通行优先级（基于距离、速度、任务紧急度）
4. 后端下发:
   → route/A: {waypoints: [...], hold_at: 3}  // 在航点3等待
   → route/B: {waypoints: [...], priority: 1}  // 优先通行
5. A 到达航点3 → 停车等待
6. B 通过交叉区域
7. 后端检测 B 已通过 → 下发 route/A: {resume: true}
8. A 恢复行驶
```

- 前端新增参数面板 + 栅格可视化
- **双模式并行：后端决策 vs ESP32 决策可切换**

#### Phase 4：高级功能（2周）

- 多车调度
- 长期地图构建（SLAM）

- **完全切换到 ESP32 决策 + 后端辅助**

### 九、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| ESP32 内存不足 | 中 | 栅格地图降级到 15×15 | 预留 3 档栅格尺寸 |
| 双核任务竞争 | 低 | WiFi 扫描影响 MQTT | 已用 Core 隔离 + 异步扫描 |
| 行为树配置冲突 | 中 | 后端下发和本地行为不一致 | override 模式明确优先级 |
| 栅格快照上报丢包 | 低 | 后端地图不完整 | QoS1 + 重传 + 本地缓存 |
| ESP32 OTA 失败 | 低 | 固件损坏 | 双分区 OTA + 回滚机制 |
| 参数下发延迟 | 低 | 调参不实时 | config 主题 QoS1 + ACK 机制 |

### 十、性能预期

| 指标 | 当前（纯后端） | 混合架构 |
|------|--------------|---------|
